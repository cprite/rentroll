**Branch:** `sprint6-court-packet` (from `main` @ `cf09e79`). Code commit `11fa855`, plus this report. Nothing pushed, `main` not touched. Real DB `data/rentroll.db` was only read; every test ran on `$TMPDIR/s6real/test.db`.

## What was built
- **`GET /api/rent-periods/:id/court-packet.pdf`** returns `Content-Type: application/pdf` as a download named `rentroll-unit-2-2026-11-payment-record.pdf`. A bad id returns 400 and an unknown id returns 404 (JSON).
- **`GET /api/rent-periods/:id/court-packet.json`** returns exactly the data the PDF is rendered from, so the two can be diffed.
- **`lib/court-packet.js`** is read-only and uses **pdfkit 0.20.2** (pure JS, `npm install` was clean with 0 vulnerabilities and no native build). It uses the standard Helvetica font, US Letter, and puts page numbers on every page. The PDF has these sections:
  1. **Header:**
     - unit and address, tenant name, email and phone, rent amount, due date;
     - the generated-at timestamp (UTC) and the as-of date;
     - the rent_period id and ledger row ids;
     - the disclaimer: "This is a record generated by RentRoll from PayPal transaction data. It is not legal advice."
  2. **Balance and status:**
     - PAID IN FULL, PARTIALLY PAID or UNPAID, computed from the COMPLETED rows in the `payment` table. The cached `rent_period` columns are not used.
     - The amount outstanding and the days overdue.
     - Any amount still processing at PayPal.
     - The approved plan's next installment and whether it is overdue.
     - The lease late-fee rule and whether it has been triggered. The report states plainly that RentRoll does not add late fees to the balance.
  3. **Payments (PayPal references):** one block per payment row, failed attempts included. Each block shows:
     - paid-at time, PayPal order id, capture id, amount, fee and net;
     - custom_id and debug_id;
     - webhook confirmation: the PayPal event id, **the time PayPal created the event**, the time RentRoll recorded it, and **the signature verification result from PayPal's `verify-webhook-signature`**. A payment captured but not yet confirmed says so.
  4. **Payment plans:** status and the installments with their state (PAID, DUE, OVERDUE).
  5. **Chronological ledger:** every `event_log` row for the rent period, ordered by `at` then `id`. Columns are time (UTC), a plain-English event label, row id and actor, details, and amount.
     - Reminder texts and tenant messages appear in full, taken from the reminder payload and the `message` table. The stored one-line summaries cut them off.
     - Webhook rows add the PayPal event id, the time PayPal created it, and the verification result.
  6. **Integrity:** a SHA-256 over the exact ledger rows included (id, at, kind, actor, summary, payload_json, paypal_event_id), with a note that the table is append-only (triggers), not tamper-proof.
- **Dashboard:** every unit cell now has a **"Download court packet (PDF)"** link styled as an outline button.
- **Small fix in the webhook handler:** it now stores the PayPal **order id** (`resource.supplementary_data.related_ids.order_id`) on payment rows that were created or confirmed by a webhook. Before this, such rows had no order id.
- **`scripts/sprint6-test.sh`** is the real end-to-end test. **`scripts/sprint6-verify-pdf.py`** checks a PDF's structure and compares its text with the JSON.
- **`samples/court-packet-example.pdf`** (plus `.json` and the `pdftotext` `.txt`) is committed. It is clean demo data: the fictional seed tenants (`*.example.com`) and PayPal sandbox ids.

### Where each part of the sample's history came from (being honest about it)
- **Payment #1 ($500, capture `3PW203477K501833J`)** is a **real sandbox capture made during the Sprint 4 test** at 00:42Z. PayPal's real signed webhook for it (`WH-3V04…`) was copied, read-only, from the rotated live log. The test server ingested it at startup, and PayPal's `verify-webhook-signature` returned **SUCCESS** again. As a result, the payment's "paid at" (00:42:56) and "PayPal event created" (00:43:01) times are earlier than the "Rent period opened" row (01:32Z), because the throwaway DB was seeded afterwards. The packet prints both the PayPal time and the RentRoll recorded time, so a reader can see what happened. A real tenant's history would not have this inversion.
- **The reminder (firm, $1,300 owed), the plan and its approval** were produced live in this run, by the real LLM and the real endpoints.
- **Payment #2 ($650, plan installment 1)** is a **new real sandbox capture from this run**. The steps were:
  1. PayPal delivered the signed webhook for it to the **live** service about 16 s later.
  2. The live service logged it as "unmatched", because rp941 doesn't exist in the real DB. That is the +940 offset working.
  3. The script copied that one line from the live log (read-only) into the test log and ingested it.
  4. Verification returned SUCCESS, and the payment is now webhook-confirmed.

## Known limits
- I did no visual check. Layout was judged from `pdftotext -layout` output and the PDF parsers only. Very long cells wrap and table rows break across pages, but this was only exercised up to 2 pages.
- Standard PDF fonts are WinAnsi only. Characters outside Latin-1 (for example emoji in a tenant's text) are replaced with `?`, while `→`, `✓` and `·` are mapped to ASCII. Embedding a TTF font would fix this if needed.
- The endpoint is public through the Funnel, like `/api/rent-periods` (it exposes tenant PII). The existing TODO about adding auth before real tenants also covers this route.
- "Court-ready" means a printable, chronological record with real PayPal references and verification results. It is not a legal filing format, and the PDF says it is not legal advice.
